# R1 — How to write instruction packs an LLM actually applies, and how to prove it

Scope note: DevDigest's "skills" are always-injected markdown, not Claude Agent Skills (no
description-triggering, no progressive disclosure by relevance). Anthropic's Agent Skills
guidance is cited for what transfers to a flat, always-on prompt block — triggering-specific
advice is flagged as non-transferable.

## Actionable principles

**1. A rule earns its place only if the model doesn't already do it unprompted — verify with a baseline, don't assume.** Anthropic's own authoring loop is "build evaluations first," run the model without the skill, document the actual gap, then write "just enough content to address the gaps" (skill-authoring best-practices doc). This directly explains DevDigest finding 1: 59% of the 56 rules were general knowledge the no-skill baseline already had, so they had nothing to add.

**2. Scope every exemption to the rule that states it — nothing in a flat prompt tells a model an exception is local.** The instruction-hierarchy work shows models need to be explicitly taught which instruction outranks which; without that signal they resolve conflicts by proximity or repetition, not by the author's intended scope. This is exactly DevDigest finding 2: `semver-discipline`'s "do not flag" bled into `breaking-change`'s catch because nothing marked the exemption as local.

**3. Prefer positive, checkable phrasing over "do not X" bans.** A recent mechanistic study argues that naming a forbidden token/behavior can itself raise the model's probability of producing it ("the very act of naming a forbidden word primes the model to produce it") — treat this as a plausible mechanism, not settled fact (single-author, non-peer-reviewed preprint). Independently, negation is a well-documented weak spot for LLMs generally. This is a candidate explanation for finding 2 and a concrete rewrite instruction: state the required behavior, not the forbidden one.

**4. Total instruction volume trades against reliability — smaller always-on rule sets, and order matters.** Two independent literatures back this: position in context has a U-shaped effect on use (Lost in the Middle), and accuracy drops as the number of simultaneous constraints/turns grows (FollowBench, Multi-IF: o1-preview falls from 0.877 to 0.707 accuracy from turn 1 to turn 3 as constraints accumulate). This matches DevDigest finding 3 directly (one skill catches, five miss; moving the key skill last restored the catch) and finding 6 (volume degrades even with neutral prose).

**5. Put severity in the rule as an explicit, observable threshold — not in a separate role prompt, and not left to inference.** Anthropic's agent-eval guidance: use "clear, structured rubrics to grade each dimension... isolated LLM-as-judge rather than one grading all dimensions," and calibrate LLM rubrics against human judgment. IFEval's whole design principle is "verifiable instructions" — a check a grader can execute without judgment calls. This maps onto finding 5: severity lived in the agent's role prompt, invisible to the skill author, while every repo-specific rule sat at WARNING/unrated and could never block.

**6. A terse rule that works on a reasoning model can silently do nothing on one that doesn't reason before answering — test on the actual target model.** Anthropic's own checklist item is "tested with Haiku, Sonnet, and Opus" specifically because a skill effective on a strong reasoner may need more explicit structure for a weaker/faster one. This is finding 4 almost verbatim: the same terse rule went 6/6 on a reasoning provider and 0/6 on two non-reasoning ones.

**7. Build the with-skill/without-skill eval before writing rule prose, and run each condition more than once.** Both Anthropic ("Build evaluations first," "at least three evaluations," success criteria before instructions) and OpenAI (define the eval objective before the eval) treat this as the actual authoring loop, not a QA afterthought. Anthropic's agent-eval piece adds why a single run is not enough: pass@k (any success in k tries) and pass^k (all k succeed) diverge sharply, and "a 0% pass rate across many trials is most often a signal of a broken task, not an incapable agent" — i.e., a single failing run could be the grader, not the skill.

**8. Write the assertion so a plausible near-miss fails it, not just so a correct answer passes it.** The skill-creator's own grader agent treats "correct filename but wrong content" as a fail, and explicitly hunts for assertions "trivially satisfied" by a wrong output. The CheckList paper's whole argument is that aggregate accuracy hides exactly these failures; a checklist of specific, adversarial-leaning items catches ~3x more bugs than ad hoc testing. Applied to DevDigest: an assertion for "flags the breaking change" should be written so a skill that flags it *and* suppresses it via its own "do not flag" clause still fails.

## Sources

1. **Skill authoring best practices** — Anthropic, https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices, undated (current docs). Type: official doc. Takeaways: (a) "concise is key" — assume the model already knows general facts, only pay for what it doesn't; (b) match "degrees of freedom" (high/medium/low) to how fragile the task is; (c) "build evaluations first," 3-step gap→eval→minimal-instructions loop; (d) test across model tiers (Haiku/Sonnet/Opus) because what works for one may not for another. Transfers: the "assume competence, don't restate" principle and the eval-first loop directly (findings 1, 4). Does NOT transfer: description-writing/triggering mechanics — DevDigest rules are always injected, nothing chooses them by description. Supports findings 1, 4.

2. **Introducing Agent Skills** — Anthropic (Claude), https://claude.com/blog/skills (redirected from anthropic.com/news/skills), undated (2025 launch post). Type: engineering/product blog. Takeaways: (a) skills exist specifically to avoid "monolithic system prompts that consume tokens regardless of relevance" — i.e., the progressive-disclosure premise doesn't hold for an always-injected rule set; (b) "only loads what's needed, when it's needed" is the core design bet, which DevDigest's architecture structurally can't use; (c) composability across multiple skills is treated as a feature, with no warning about cross-skill interference. New/extends: names the architecture DevDigest's skills don't have, which sharpens why finding 3 (skills competing) is a DevDigest-specific failure mode, not one Anthropic's design anticipates.

3. **skill-creator SKILL.md** — local skill, `/Users/Glebazzz/.claude/skills/synced/6c1f793a-cc4b-41ef-9655-fc8556486402_2ee7a444-c415-4231-b1a6-a6fa3ed70c30/skill-creator/SKILL.md`, undated. Type: tool docs (local). Takeaways: (a) "explain to the model why things are important in lieu of heavy-handed musty MUSTs" — ALL-CAPS/NEVER framing is flagged as a yellow flag, reframe with reasoning instead; (b) evaluation-driven iteration: spawn with-skill AND baseline runs in the same turn, grade with named, discriminating assertions; (c) "keep the prompt lean... if it looks like the skill is making the model waste time on unproductive things, cut that part and see what happens." Supports findings 1 (restating known things wastes budget) and the general "test, don't assume" stance behind finding 4.

4. **skill-creator agents/grader.md** — local, same skill dir, `agents/grader.md`. Type: tool docs (local). Takeaways: (a) "a passing grade on a weak assertion is worse than useless — it creates false confidence"; (b) PASS requires evidence that reflects "genuine task completion, not just surface-level compliance"; (c) explicitly hunts for assertions that would "also pass for a clearly wrong output." Supports finding 5 and principle 8 — a grading discipline DevDigest's own severity/assertion design should copy.

5. **skill-creator agents/comparator.md** — local, same skill dir, `agents/comparator.md`. Type: tool docs (local). Takeaways: (a) blind A/B comparison to remove bias toward a known-authorship output; (b) builds a task-specific rubric with named criteria (correctness, completeness, accuracy / organization, formatting, usability) rather than one holistic number; (c) treats rubric score as primary, assertion pass-rate as secondary evidence. Extends finding 4's practices with a concrete analytic-rubric template.

6. **skill-creator references/schemas.md** — local, same skill dir, `references/schemas.md`. Type: tool docs (local). Takeaways: exact JSON contract for evals/grading/benchmark artifacts — most relevant fact is that `benchmark.json` tracks `pass_rate`, `time_seconds`, `tokens` per configuration with mean±stddev, i.e. variance is a first-class field, not an afterthought. Supports principle 7 (variance across runs).

7. **Demystifying evals for AI agents** — Anthropic, https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents, undated (2025/2026). Type: engineering blog. Takeaways: (a) "grade what the agent produced, not the path it took"; (b) use "clear, structured rubrics... isolated LLM-as-judge rather than using one to grade all dimensions"; (c) pass@k vs pass^k diverge sharply at k=10, and "a 0% pass rate across many trials is most often a signal of a broken task, not an incapable agent"; (d) "a good task is one where two domain experts would independently reach the same pass/fail verdict." Supports findings 5 and directly informs principles 5, 7.

8. **First steps: develop test cases** — Anthropic, https://platform.claude.com/docs/en/docs/build-with-claude/develop-tests (redirected from docs.anthropic.com), undated. Type: official doc. Takeaways: (a) SMART success criteria (Specific/Measurable/Achievable/Relevant) — "Bad: safe outputs. Good: <0.1% of outputs flagged for toxicity in 10,000 trials"; (b) "more questions with slightly lower-signal automated grading is better than fewer questions with high-quality hand grading"; (c) best practice to grade with a different model than the one that generated the output; (d) always include edge cases (irrelevant/nonexistent input, overly long input, ambiguity). Supports principle 7, extends finding 5 (severity/threshold must be numeric and stated up front, not implied).

9. **Evaluation best practices** — OpenAI, https://developers.openai.com/api/docs/guides/evaluation-best-practices, undated. Type: official doc. Takeaways: (a) "define eval objective" before building anything; (b) mix production data with expert-authored edge/adversarial cases; (c) for LLM-judges, "use pairwise comparison or pass/fail for more reliability" over free-form scoring, and calibrate with human feedback. Supports principle 7; corroborates Anthropic's guidance from an independent lab (triangulation, not new).

10. **The Instruction Hierarchy: Training LLMs to Prioritize Privileged Instructions** — Wallace, Xiao, Leike, Weng, Heidecke, Beutel (OpenAI), https://arxiv.org/abs/2404.13208, April 19 2024. Type: paper. Takeaways: (a) untrained models treat system and user text as equal priority by default — priority must be explicitly taught, it isn't inferred; (b) a model can be trained to "selectively ignore lower-privileged instructions," but this is a trained capability, not a default one; (c) the fix generalizes to unseen conflict types when the hierarchy signal is present during training. Directly explains the mechanism behind finding 2: DevDigest's flat prompt gives the model no hierarchy signal, so a global-sounding exemption in one skill overrides another skill's catch. Supports finding 2; principle 2.

11. **Lost in the Middle: How Language Models Use Long Contexts** — Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni, Liang, https://arxiv.org/abs/2307.03172 (TACL 2024, vol. 12). Type: paper. Takeaways: (a) "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle"; (b) the effect holds even for models built for long context; (c) implies position, not just presence, of an instruction determines whether it's used. Supports finding 3 (moving the key skill last restored the catch) and finding 6 (heading-collision didn't matter but position plausibly does); principle 4.

12. **Multi-IF: Benchmarking LLMs on Multi-Turn and Multilingual Instructions Following** — He, Jin, Wang, Bi, Mandyam, et al. (Meta), https://arxiv.org/abs/2410.15553, Oct 21 2024 (rev. Nov 13 2024). Type: paper. Takeaways: (a) accuracy drops as constraints accumulate across turns — o1-preview: 0.877 → 0.707 from turn 1 to turn 3; (b) the drop holds across all tested models, not one weak model; (c) multilingual variants make it worse, i.e., the effect compounds with any added complexity. Supports finding 3 ("more skills, fewer catches"); principle 4.

13. **FollowBench: A Multi-level Fine-grained Constraints Following Benchmark for LLMs** — Jiang, Wang, Zeng, Zhong, Li, Mi, Shang, Jiang, Liu, Wang, ACL 2024 (Bangkok), https://github.com/YJiangcm/FollowBench (paper venue: ACL 2024 proceedings). Type: paper (accessed via project page, not the PDF directly — mark as **not fully verified**, only the project page's own description was read, not the full paper text). Takeaways: (a) benchmark incrementally adds one constraint at a time to the same base instruction to isolate the effect of constraint count; (b) introduces a "Consistent Satisfaction Levels" metric — how many consecutive constraint levels a model can still satisfy. Supports finding 3/principle 4 as a second, independent benchmark family; treat the specific numbers as unverified since I read the repo page, not the paper PDF.

14. **Instruction-Following Evaluation for Large Language Models (IFEval)** — Zhou, Lu, Mishra, Brahma, Basu, Luan, Zhou, Hou (Google), https://arxiv.org/abs/2311.07911, Nov 14 2023. Type: paper. Takeaways: (a) defines "verifiable instructions" — objective, checkable constraints ("more than 400 words," "mention AI ≥3 times") — as the antidote to expensive/biased human or LLM grading; (b) ~500 prompts across 25 instruction types, each with one or more such constraints. This is the direct template for principle 5 (severity/pass criteria as an explicit, checkable threshold rather than a vague standard) and for how DevDigest's own checks should be phrased.

15. **Semantic Gravity Wells: Why Negative Constraints Backfire** — Shailesh Rana, https://arxiv.org/abs/2601.08070, Jan 12 2026. Type: paper, **not verified as peer-reviewed — single author, very recent preprint, treat as a plausible-mechanism hypothesis, not established fact**. Takeaways: (a) claims a logistic relationship between "semantic pressure" (the model's intrinsic probability of the forbidden token) and violation likelihood; (b) "the very act of naming a forbidden word primes the model to produce it" — proposed as the dominant failure mode (87.5% of cases in their setup) versus a rarer late-layer override failure (12.5%). New: offers a candidate mechanism for why "do not flag X" clauses might backfire, extending (speculatively) finding 2. Flag this source's confidence level explicitly if cited in the README.

16. **Negation: A Pink Elephant in the Large Language Models' Room?** — Vrabcová, Kadlčík, Sojka, Štefánik, Spiegel, https://arxiv.org/abs/2503.22395, Mar 28 2025 (rev. Jun 3 2025). Type: paper. Takeaways: (a) negation is a well-documented, persistent weak spot in LLM textual-entailment performance, not limited to one model family; (b) the effect is language-dependent (worse for non-projective languages). Weaker fit than expected — this paper is about negation in entailment/reasoning, not about "do not do X" behavioral instructions specifically; cite as general corroboration that negation is hard for LLMs, not as direct evidence for finding 2/4.

17. **Beyond Accuracy: Behavioral Testing of NLP Models with CheckList** — Ribeiro, Wu, Guestrin, Singh, ACL 2020 (Best Paper). https://arxiv.org/abs/2005.04118. Type: paper. Takeaways: (a) "measuring held-out accuracy... often overestimates the performance of NLP models" — aggregate pass rate hides specific, correctable failures; (b) a matrix of specific, named test types (not one holistic judgment) found teams ~2x more tests and ~3x more bugs than ad hoc testing. This is the founding argument for checklist-style, itemized grading over a single holistic score — supports principle 8 and the general rubric/checklist section (topic 4).

18. **Judging LLM-as-a-Judge: Concerning Rubric Artifacts in LLM-based Automated Text Generation Evaluation** — Bagaria, Sundaram, Krishnan, Ravindran, https://arxiv.org/abs/2609.02942, Aug 31 2026. Type: paper. Takeaways: (a) "rubric formulations encode recoverable evaluative signal, allowing scores to be partially anticipated independently of model outputs" — i.e., a judge can be gamed by how the rubric is worded, not just by the response; (b) judges "often fail to reliably update their decisions when either the candidate response or the rubric criterion is reversed" — a reliability warning for any severity/rubric design DevDigest builds for its own LLM-judge grading. New: a caution specifically for topic 4 (rubric design) not present in Anthropic/OpenAI's own guidance — write rubric wording carefully, and stress-test it with reversed/flipped cases.

## Open questions

- Whether DevDigest's own severity levels (CRITICAL/WARNING/SUGGESTION) should be redefined as IFEval-style verifiable thresholds per rule, or whether a smaller number of coarser, well-separated bands would resist the rubric-artifact gaming problem (source 18) better than finer-grained ones.
- Whether the "put the highest-priority rule last" fix (finding 3) generalizes past the two tested fixtures, or is itself an artifact of DevDigest's specific prompt length — none of the position-effect literature found here (Lost in the Middle) was run on a non-reasoning small/mid model at DevDigest's context length, so the transfer is plausible but unverified.
- No primary source was found that studies non-reasoning models' handling of scoped instruction exemptions specifically (vs. the Instruction Hierarchy paper's reasoning-model setting) — worth a targeted search before finalizing the README if time allows.
