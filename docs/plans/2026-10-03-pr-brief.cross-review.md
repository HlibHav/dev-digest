**XR-1**  
Severity: critical  
AC/Plan section: AC-12 / step 10 (I2)  
What is wrong: The plan’s test for AC-12 relies on building the app with `NODE_ENV=development` to enable rate limiting, but the spec’s proof tag demands “red-first integration” that should run in the same environment as all other integration tests (`NODE_ENV=test`). The default cannot be changed per test without side effects (Open question 9). The AC cannot be verified as written.  
Concrete fix: Adjust the plan to implement a `buildApp` option to enable rate limiting in test mode, or accept that the integration test cannot verify AC-12 and mark it as blocked.

**XR-2**  
Severity: major  
AC/Plan section: AC-10 / step on server lane  
What is wrong: The plan does not specify how the server will ensure “serve a second generation request for the same PR with the result of the first”. While step 8 mentions an `inflight` map, no mechanism is described to guarantee that concurrent requests share the same promise and that the promise is cleared only after completion (including failures). A missing or flawed implementation could lead to duplicate calls or deadlocks.  
Concrete fix: Specify in step 8 that `inflight` is a `Map<string, Promise<PrBriefResult>>`; the service’s `generate` method checks the map first, creates and stores a new promise if absent, and removes the entry in a `finally` block after the promise settles (success or failure).

**XR-3**  
Severity: major  
AC/Plan section: AC-16 / step 9 (I1)  
What is wrong: The test for AC-16 does not verify “inject the default-branch version of a doc the PR modifies.” The plan only checks ordering and deduplication, but the spec requires that if the PR modifies a file listed in an attachment, the model should see the default-branch version, not the PR’s version. This is a key security property.  
Concrete fix: In step 9’s I1, add a case where an attached doc path matches a file changed in the PR; verify that the model input contains the text from the default-branch clone, not the PR diff.

**XR-4**  
Severity: major  
AC/Plan section: AC-9a / step 9 (I1)  
What is wrong: The plan’s verification for AC-9a only checks that the brief’s `head_sha` matches the refreshed head or stored head. It does not verify that “the head commit that matches the files it used” — i.e., that if the refresh fails, the brief uses the stored files (not refreshed) and the stored head. The test should confirm that files and head are consistent.  
Concrete fix: Extend the I1 test: when GitHub refresh fails, assert that the model input uses the stored files list (not empty) and that the stored head is stamped on the brief.

**XR-5**  
Severity: major  
AC/Plan section: AC-19 / step 9 (I1)  
What is wrong: The plan says validation uses “the file list, blast snapshot and changed ranges the model was shown for this generation, not against a re-fetch.” However, the “file list” ambiguity (Open question 6) is resolved as “the whole refreshed file list,” but the spec says validation uses “the file list the model was shown.” If files are truncated per AC-14, validation should still use the full refreshed list, not the truncated list sent to the model. The plan does not explicitly enforce this.  
Concrete fix: In step 5’s `buildValidationContext`, clarify that it receives the full `files` array (all refreshed files), not the truncated list. In step1726, ensure the service passes the full list to the validation context.

**XR-6**  
Severity: major  
AC/Plan section: AC-21a / step 5 (U2)  
What is wrong: The plan’s unit test for AC-21a includes a case “line ref 13–11 becomes 13–13” (end < start). However, the spec’s AC-21a states “an end line smaller than the start line is set equal to the start line.” The plan’s example is correct, but the test does not cover the case where start_line is valid but end_line is smaller and both are inside a changed range — the rule should still apply.  
Concrete fix: Add a test case in U2: start_line=30, end_line=25 inside a changed range 20–40 → becomes 30–30 (end set equal to start).
