## Self-review
- zod — The schemas follow the rules: shared schemas extended with `.extend`, `.nullable()` and `.optional()` used correctly, a path on the refine error, enums for fixed values, schema and type sharing one name, and unknown keys stripped by default. No issues.
- security — The contract is validation only, so no exploit paths are involved. `EvalCaseWrite.input_diff`, `input_meta.body` and `expected_output` have no max length or count, because the plan specifies only `min 1`. I did not add caps, since that would change the contract. The L1 route should set a `bodyLimit` or the caps (see Handoff).
- drizzle-orm-patterns — FK references use arrow functions, cascade and `set null` are as planned, and indexes are declared in the table callback. No issues.
- postgresql-table-design — Found: `eval_cases.source_finding_id` is an FK without an index, and Postgres does not auto-index FKs. The `ON DELETE SET NULL` from `findings` would scan `eval_cases`. Fixed by adding `eval_cases_source_finding_idx`.
- The other FK columns are covered:
  - `agent_id` is the leading column of the `(agent_id, source_finding_id)` unique index and of the suite-run indexes.
  - `workspace_id` has an index.
  - `eval_runs.suite_run_id` has an index.
- The unique `(agent_id, source_finding_id)` allows multiple NULL `source_finding_id` values per agent. That is intended: manual cases have no source finding.
- I kept `jsonb` with `.notNull()` and defaults, `timestamptz`, and `text` plus a drizzle enum. The skill's CHECK-constraint suggestion for `status` is not applied, because the repo uses drizzle text enums elsewhere.
